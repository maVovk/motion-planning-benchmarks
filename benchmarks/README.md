# Часть 1: сравнение broadphase Coal


Из корня репозитория, Ubuntu/WSL:

```sh
sudo apt-get update
sudo apt-get install -y build-essential cmake git python3-venv

python3 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install -r requirements-lock.txt
PREFIX=$(.venv/bin/python -c 'import sysconfig; print(sysconfig.get_paths()["purelib"] + "/cmeel.prefix")')

cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DCMAKE_PREFIX_PATH="$PREFIX" \
  -DMPB_BUILD_BENCHMARKS=ON -DMPB_BUILD_PLANNING=OFF
cmake --build build --target build_benchmarks
mkdir -p results
./build/coal_benchmark --benchmark_repetitions=5 \
  --benchmark_out=results/benchmark.json --benchmark_out_format=json
./build/coal_benchmark --memory > results/memory.csv
```

## Конфигурация бенчмарков

Бенчмарки конфигурируются с помощью `BenchmarkConfig`

```cpp
struct SceneConfig {
  double sphere_radius = 0.25;
  double half_extent = 10.0;
  uint32_t seed = 42;
};

struct HashConfig {
  double cell_size = 0.5;
  double half_extent = 32.0;
  std::uint32_t table_size = 10007;
};

struct QueryConfig {
  double outside_x = 30.0;
  size_t queries_per_workload = 128;
};

struct BenchmarkConfig {
  SceneConfig scene;
  HashConfig hash;
  QueryConfig query;
};
```

`SceneConfig`: `half_extent` - половина стороны куба, где размещаются сферы.  
`HashConfig`: конфиг для `SpatialHashingCollisionManager`.  
`QueryConfig`: конфигурация запросов бенчмарка.

## Выводы

На основе данных из [benchmark.json](../results/coal/benchmark.json) и
[memory.csv](../results/coal/memory.csv). Сами таблички с результатами ниже, они достаточно громоздкие. Тесты гонялись в Release сборке, собранной по инструкции из начала файла.

### `NaiveCollisionManager`

Время растёт линейно от количества сфер. Начиная с 24 µs до 177 ms. Что в целом ожидаемо - алгоритм проходит по всем сферам и ищет коллизии для них. При этом в hit режиме мы очень быстры так как сразу находим коллизию. Что удивительно, так это рост числа аллокаций. Видимо внутренний стейт алгоритма создаёт много временных объектов. Но пиковое потребление всего 0.2 Мб


### `SaPCollisionManager`

Ассимптотика всё ещё похожа на линейную от количества сфер, но при этом на порядок быстрее `naive` при рандомной нагрузке. В `hit` режиме мы работаем хуже `naive` алгоритма на 2 порядка. В пике мы тратим 3.5 Мб, что сильно больше `naive`, но это ожидаемо, т.к у нас появляется доп.структура


### `SSaPCollisionManager`

Здесь мы опять на порядок быстрее предшественника `SaPCollisionManager` и тратим меньше памяти, в пике 0.4, почти как `naive`. Доп.структура похоже является более легковесной, чем в оригинальном SaP

### `IntervalTreeCollisionManager`

`IntervalTreeCollisionManager` показывает отличное, константное, время, когда у нас таргеты находятся за сценой. Видимо поиск по дереву сразу отсеивает варианты за пределами построенной зоны. Но на поддержание дерева уходит больше памяти - 7 Мб. Рандомные запросы работают медленнее обоих SaP, видимо спуск по дереву имеет большую константу в ассимптотике. Но стоит заметить, что рост медленее, чем у SaP подобных алгоритмов. При повышении количества сфер на 4 порядка, время выросло всего на 2, в отличие от 3.

### `DynamicAABBTreeCollisionManager`


Тут объединяется преимущество `IntervalTreeCollisionManager` с константным временем работы при отсутствии коллизий с малым потреблением памяти 2 Мб и малым временем работы на всех размерах. Время работы растёт медленно, в процессе работы аллокации практически не требуются. Время инициализации также небольшое, относительно других алгоритмов.


### `DynamicAABBTreeArrayCollisionManager`

Здесь мы имеет DynamicAABB, но с другим layout внутренней структуры. Отсюда берётся чуть большее время инициализации, но мы получаем итого меньше аллокаций и чуть более быструю работу, скорее всего за счёт memory оптимизаций OS и CPU. 

### `SpatialHashingCollisionManager`

Результаты здесь хуже AABB, но ключевые особенности заметны - практически идентичное время работы и затраты памяти до определённого момента. Потому видимо корзины "забиваются" и у нас получается множество коллизий. Подтюнив параметры я думаю можно добить времени работы, схожего с AABB, потому что в текущем эксперименты количество кандидатов у хэш индекса при 10000 сферах было в среднем 20, тогда как у AABB деревьев - 0.77. Этот алгоритм может быть хороший примером обмена RAM на CPU time. Если у нас много RAM, мы можем сделать больше бакетов и сделать коллизий меньше.

## Результаты

Время — медиана `cpu_time` в микросекундах. `initialize` — создание менеджера, регистрация объектов и `setup()`
(без создания сцены). Замеры `outside_miss`, `hit` и `random` происзводились на 128 запросах. Поэтому время на один запрос можно получить, поделив значение из таблицы на 128.

`outside_miss` — таргеты вне сцены(без столкновений), `hit` — таргеты совпадают со сферами(100% столкновения),
`random` — случайные запросы внутри области сцены. Поиск останавливается на первом столкновении.

Память: `retained` — оставшаяся выделенная память,
`peak` — пиковая память этапа (`*_peak_extra_bytes`),
`allocations` — число аллокаций.
