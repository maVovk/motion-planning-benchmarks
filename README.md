# Collision and motion planning benchmarks

Репозиторий для двух частей тестового задания:

1. **Готово:** сравнение широких фаз coal для сфер — код и результаты в корне и `results/`.
2. **Предстоит:** сравнение RRTConnect через VAMP и OMPL + coal для UR5,
   профилирование `perf` и flamegraph’ы. Эта часть будет выполняться отдельно
   на Linux-машине с поддержкой AVX.

## Coal: сферы против целевой сферы

Реализация пункта 1 тестового задания. Весь C++ код — в `main.cpp`.
`run_benchmark.py` только последовательно запускает бинарник и агрегирует CSV.

## Сборка на macOS arm64

```sh
python3 -m venv .venv
.venv/bin/pip install -r requirements-lock.txt
PREFIX=$(.venv/bin/python -c 'import sysconfig; print(sysconfig.get_paths()["purelib"] + "/cmeel.prefix")')
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DCMAKE_PREFIX_PATH="$PREFIX"
cmake --build build -j 4
.venv/bin/python run_benchmark.py
```

Cmeel wheel содержит настоящие C++ headers, dylib и CMake package coal;
Python bindings не участвуют в измерении. Версии зависимостей закреплены.
Пример отдельного запуска: `./build/coal_benchmark tree 10000 42`.
Бенчмарк памяти использует API macOS и требует адаптации для Linux.

## Методика

* Все 7 дискретных менеджеров из `coal/broadphase/broadphase.h`: Naive,
  SaP, SSaP, IntervalTree, DynamicAABBTree, DynamicAABBTreeArray, SpatialHashing.
  Continuous manager — интерфейс для другой задачи, непрерывной коллизии.
* N = 1, 10, 100, 1000, 10000. Все сферы, включая целевую, радиуса 0.25.
  Центры препятствий равномерно распределены в кубе [-10,10]^3.
  С ростом N плотность растёт; это сравнение в фиксированном объёме.
* SpatialHashing: cell_size=0.5, bounds=[-32,32]^3, table_size=10007.
  Параметры одинаковы для всех N; оптимизация параметров не выполнялась.
* 128 позиций цели на каждый сценарий: `outside_miss` (x=30),
  `hit` (центр одной из первых min(N,128) сфер), `random` (внутри куба).
  Все менеджеры получают одни и те же сцены/цели для данного seed.
  Порядок hit-запросов может благоприятствовать Naive; random — более
  представительная смешанная нагрузка. Outside miss — намеренно лёгкий
  случай для деревьев, способных отсечь всю сцену по корневому AABB.
* Запрос — `manager.collide(target, callback)` с ранним выходом после
  первой **реальной** коллизии. Callback вызывает narrow phase coal,
  сбрасывает CollisionResult и запрашивает максимум один контакт без его
  геометрии. Время включает reset callback, обход broad phase, narrow phase
  и накопление результата в volatile счётчик. Перемещение цели и пересчёт
  её AABB заранее, вне таймера. Сцена статическая, обновление индекса не измеряется.
* До таймера каждый из 384 запросов проверяется в двух режимах:
  полный подсчёт и ранний выход. Oracle — независимая точная проверка
  `squaredNorm(center-target) <= (r1+r2)^2` для всех сфер.
  Ошибка проверки завершает процесс ненулевым кодом. Эти запросы также
  прогревают код, кэши и временные аллокации менеджера.
* Время одного запроса — медиана 9 пакетов по 512 запросов
  (4 обхода набора из 128 позиций). Clock — steady_clock.
  Измерения отражают повторные запросы с прогретыми кэшами.
* Время инициализации — constructor + registerObjects + setup;
  деструктор не включён. Создание CollisionObject/геометрии/AABB измеряется
  отдельно (`scene_us`). На процесс приходится одно построение индекса;
  для малых N его время шумное, в том числе из-за первого обращения к коду.
* Пять отдельных процессов на (менеджер,N), seeds 42..46. Порядок всех
  175 запусков перемешан фиксированным seed 2026; процессы идут последовательно.
  В summary — медианы пяти процессов, а также min/max query_us между seeds.
  Разброс между seeds включает и различия сцен, и системный шум.

## Память и ограничения

`malloc_zone_statistics(nullptr).size_in_use` — занятые байты malloc всех зон
на macOS. `scene_heap_bytes` — прирост при создании N отдельных геометрий и
CollisionObject; `index_heap_bytes` — прирост после constructor/register/setup.
Это retained heap, **не пик** временной памяти построения или запроса.
Заранее выделенные массивы указателей/центров, цели и служебные данные
бенчмарка исключены из этих дельт. Сферы не разделяют один объект геометрии.
Приблизительно ещё 40N байт приходится на capacity массивов сцены в harness.

В raw также записан RSS процесса в байтах до сцены, после сцены и после
индекса (`mach_task_basic_info`). RSS включает код/библиотеки, allocator slack,
страницы стека и служебные данные. Его дельты округляются по страницам и
не являются точным размером структуры. Ни RSS, ни heap snapshots не измеряют
пиковые временные аллокации в callback. Это ограничение метода, а не нулевое
потребление памяти запросами.

Не выполнялись привязка к ядру, отключение фоновых приложений или контроль
частоты/температуры. Очень короткие запросы порядка наносекунд следует читать
как порядок величины. Выводы относятся к этой геометрии, распределению,
настройкам и статической сцене; переносить их на меши и динамические сцены нельзя.

Исходный проект: https://github.com/coal-library/coal
